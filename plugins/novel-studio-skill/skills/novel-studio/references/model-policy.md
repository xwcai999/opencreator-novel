# 模型角色策略

## 原则

- 不在 Skill、模板或项目校验中硬编码具体模型版本、Provider 或 API。
- 由当前运行环境解析实际模型；不可用时回退到当前任务模型，不阻断现有创作流程。
- 模型名称不等于审稿独立性。只有上下文隔离、输入边界和正文版本独立时，才能记录独立审稿证据。
- 同一卷优先保持固定写手角色；模型变更时先做短样章对比，不直接批量续写。
- 每本小说从自己的读者契约、控制场景和文风档案重新校准；不得自动继承或读取其他小说的文风档案。

## 角色分配

| 角色 | 首要能力 | 稳定性要求 | 最小上下文 |
| --- | --- | --- | --- |
| 主 Agent／总编 | 规划、连续性、证据裁决 | 全项目保持规则一致 | 权威状态、设定、细纲、最终正文 |
| 固定写手 | 中文叙事、人物声音、场景展开 | 同一卷尽量固定 | 控制卡、active 文风档案、必要前文 |
| 首次读者 | 阅读接受、困惑与耐心判断 | 必须隔离作者解释 | 正文、必要前章、读者画像 |
| 连续性／文体审稿者 | 事实、因果、声音和同型结构 | 与写手分离上下文 | 正文、权威规则、必要前文 |

## 运行策略

1. 默认使用当前任务模型完成主 Agent 工作。
2. 用户明确授权 subagent 且环境支持时，固定一个写手顺序负责当前卷；相邻章节不得并行生成。
3. 审稿优先使用全新隔离上下文；可用不同模型，但不把“不同模型”设为硬条件。
4. 只有一个模型时，用独立输入包分别执行写手、首次读者和审稿角色，不让审稿上下文看到作者解释。
5. 模型切换只影响后续候选文本，不得反向改写 accepted 章节或清空已有审查证据。

## 降级规则

- 无法建立独立上下文：合并为作者型审查，并在交付中说明未完成独立读者审查。
- 文风档案缺失或 inactive：沿用读者契约、人物档案和最近 accepted 正文，不创建临时隐式规则。
- 指定模型不可用：使用当前任务模型，报告实际降级，不擅自联网或配置其他 Provider。
- 用户明确指定模型或写手策略时，以用户选择为准，但仍执行确定性硬门禁。
